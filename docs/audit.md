# Аудит исходного состояния Publication Monitor v2

Дата: 23 октября 2026 года. Ветка: `feature/publication-monitor-v2-20261023`.

Это исходный архитектурный аудит для реализации v2, а не заключение о готовности конечной версии. Он учитывает код и незакоммиченные изменения, существовавшие при начале работ. Исправления команды после этого среза отражаются в итоговой матрице требований и отчете проверки. Аудитор не менял исходный код, не выполнял миграции и не обращался к рабочей БД; `.env` не читался.

## Источники и границы проверки

- Полностью прочитано ТЗ из `docs/specification-source.txt`: извлечение текста исходного `Техническое задание.docx`, включая все семь таблиц организационной структуры, пользователей, плана и отчетности.
- Прочитано пользовательское задание `goal-objective.md`. Оно определяет обязательный стек, канонические имена ролей и дополнительные требования к приемке. Текст ТЗ использован как описание предметной области, а не как отдельные инструкции на выполнение действий.
- Изучены фабрика Flask, конфигурация, маршруты всех модулей, модели, сервисы планов/публикаций/выгрузок, миграции, шаблоны общей оболочки и аналитики, существующие тесты.
- Наличие теста не означает, что он прошел: результаты запуска тестов, браузерной проверки и PostgreSQL-миграций должен фиксировать итоговый `docs/testing.md`.
- В исходной рабочей копии много пользовательских изменений. По уточнению пользователя они должны остаться незакоммиченными; нельзя включать целиком измененные при старте файлы в новые коммиты.

## Матрица прав

Канонические роли задания: TECH_ADMIN, MONITOR, DEPARTMENT_HEAD. Исходный код использует ADMIN вместо MONITOR. Это несовпадение контракта, а не наличие четвертой разрешенной роли. Нужна миграция существующих значений с переходной совместимостью.

| Действие | TECH_ADMIN | MONITOR (исходный ADMIN) | DEPARTMENT_HEAD |
|---|---|---|---|
| Пользователи и кафедры | Управление | Нет | Нет |
| Состояние системы и backup | Да | Нет | Нет |
| Восстановление backup | Отсутствует | Нет | Нет |
| Журнал | Чтение/поиск/CSV | Чтение/поиск | Нет |
| Справочники | Нет | Управление | Выбор в формах |
| Планы | Нет | Все, согласование/возврат/оценка | Свои, заполнение/отправка/запрос корректировки |
| Публикации | Нет | Все, только проверка/комментарии/решения дубликатов | Свои, ведение/статусы/файлы |
| Сотрудники | Нет | Нет | Свои, управление |
| Аналитика/отчеты | Нет | Все кафедры | Своя кафедра |
| Комментарии/уведомления | Нет | По доступным объектам/личные | Свои объекты/личные |

Проверки основаны на серверной записи User, decorators и `ensure_department_access`, а не только на сокрытии кнопок. TECH_ADMIN не включен в согласование публикаций.

## Безопасность: имеющиеся меры и незакрытые проверки

Подтверждены по коду: BCrypt; серверная проверка активности/роли; password stamp для отзыва сессии при изменении пароля; очистка сессии при входе; проверка локального next URL; POST для выхода; глобальная CSRF-защита; ограничение login; cookie HttpOnly/SameSite/Secure для production; запрет debug в production; SQLAlchemy-параметризация; объектный доступ к планам, публикациям и вложениям; запрет изменения публикаций монитором; аудит административных действий; CSV/XLSX/PDF escaping; случайные имена загрузок вне static; backup без пароля в argv, безопасное разрешение пути backup и доступ только TECH_ADMIN.

Следующие пункты требуют проверки исполнения или эксплуатационной настройки и не названы подтвержденными уязвимостями:

- Ограничитель по умолчанию использует `memory://`: для нескольких WSGI workers требуется общее хранилище. Это ограничение развертывания, а не доказанный обход в текущем окружении.
- При изменении статуса/проверке публикаций не применяются те же row locks, что в планах. Необходим тест конкурирующего редактирования и проверки, прежде чем заявлять сохранение инварианта проверенной карточки.
- Удаление файла до фиксации транзакции БД может оставить Attachment без физического файла при ошибке commit. Нужно согласовать rollback/компенсацию файловой операции.
- Наличие сигнатуры файла не означает антивирусную проверку. Обязательны content checks, лимиты и скачивание как attachment; интеграция с антивирусом зависит от инфраструктуры.
- Политика CSP допускает inline scripts/styles и jsdelivr. Это текущее ограничение frontend, само по себе не доказательство XSS. На внутренней сети желательно локально хранить зависимости.
- `AuditLog` защищен от изменения через пользовательские маршруты; права учетной записи БД и ограничение DBA находятся вне этой статической проверки.

## UI/UX и продуктовые ограничения

- Общий layout, мобильный offcanvas, RU/KK и responsive tables уже есть. Исходная тема использует фиолетовый акцент (`theme-color #5314CD`), тогда как целевой стиль требует сдержанный синий.
- У количественной таблицы из ТЗ нет пользовательского сценария; добавление одной именной строки за раз не заменяет количественное планирование.
- «Нет плана» необходимо отличать от нулевого выполнения во всех карточках и отчетах.
- В формах сверки нужно показать правило первой аффилиации и ручной характер проверки Scopus/WOS/КОКСНВО.
- В старой главной панели KPI «опубликовано» считают все PUBLISHED, а расчет исполнения — только проверенные APPROVED. Подписи должны объяснять это различие.
- Требуется браузерная проверка 320 px/планшет/desktop, клавиатуры, focus и контраста. Статический просмотр Bootstrap-классов не подтверждает WCAG 2.2 AA.
- SMTP, университетский логотип, критерии оценки и внутренние регламенты явно не предоставлены в ТЗ. Их нельзя подменять фиктивной реализацией.

## План безопасной миграции

1. Сохранить исходные рабочие изменения; не stage пользовательские файлы целиком. Новые документы и новые модули коммитить отдельно в feature-ветке.
2. Зафиксировать контракт существующих маршрутов, базовые RBAC/workflow проверки и baseline числа записей только на тестовой копии.
3. Выполнить аддитивные миграции: факультеты и nullable связь кафедры; цели плана с unique plan/type; связи реальных сверхплановых публикаций; каноническая роль; partial unique ответственного.
4. Перед уникальным индексом проверить существующие конфликты и остановиться с понятной диагностикой. Не удалять и не выбирать «главного» пользователя автоматически.
5. Для старых планов сохранить item-based знаменатель как fallback. Для новых количественных целей использовать согласованное правило без суммы «цели + уже учтенные именные работы».
6. Сохранять утвержденный snapshot на период корректировки; повторное утверждение не создает вторую publication для существующего PlanItem.
7. Добавить обязательные справочные коды без удаления старых. Не менять научную классификацию существующих данных без явного действия пользователя.
8. Прогнать upgrade и проверку целостности в отдельной PostgreSQL БД; сравнить число пользователей, планов, публикаций, вложений и истории. Downgrade не запускать на рабочей БД.
9. Проверить восстановление резервной копии в изолированную БД и отдельно сохранность каталога uploads. Дамп БД сам по себе не включает файлы.
10. Выполнить финальную проверку pytest, Ruff, миграций, запуска, выгрузок и UI; только после этого обновить конечные статусы требований.

## Решение по количественному и поименному планированию

ТЗ одновременно описывает список конкретных статей и количественную таблицу. Это два представления одного объема нагрузки, а не два суммируемых плана. Рекомендуется:

- хранить целевое количество отдельно для каждого типа;
- считать именные пункты детализацией соответствующего типа, не прибавляя их к явно заданной цели;
- для исторических типов без количественной цели использовать число именных пунктов;
- создавать рабочую публикацию только для настоящего именного пункта; количественная цель не должна порождать фиктивные названия;
- разрешать регистрацию дополнительной фактической работы в пределах утвержденного плана и типа, чтобы отчет мог показать 120%;
- подсчитывать каждую реальную работу один раз внутри принятой схемы классификации; правило одновременной индексации Scopus/WOS требует явного решения университета.

До утверждения числовой шкалы оценок допустимы объективные значения плана, факта, процента и просроченных сроков. Нельзя выдавать выбранные разработчиком пороги за утвержденный университетом норматив.
